# Migrate from 0.1 to 0.2

`0.2.0` moves DSHX from the DSH `0.1.x` contract generation to `0.2.x`. The active adapter is `protocol-2`; the verified runtime baseline is a build of source tag `dsh-v0.2.1-rc.2`. This is a breaking release: `@deepseek-ai/dsh-client-runtime`, the DSHX Settings provider, and the previous Conversation/Connection bindings are removed rather than kept behind aliases.

> The npm `@deepseek-ai/dsh@0.2.1-rc.2` artifact currently ships stale profile-boot code. Use a source build of the tag for development and smoke testing until upstream republishes it. The adapter records the verification source as `source`, so npm `0.2.1-rc.2` is treated as experimental.

## 1. Update the project metadata

```json
{
  "devDependencies": {
    "@becomeopc/dshx": "0.2.0-preview.0",
    "@deepseek-ai/dsh": "0.2.1-rc.2"
  },
  "peerDependencies": {
    "@deepseek-ai/dsh": ">=0.2.1-rc.2 <0.3.0-0"
  },
  "engines": {
    "dsh": ">=0.2.1-rc.2 <0.3.0-0"
  }
}
```

`engines.dsh` is the preferred public support declaration; `peerDependencies["@deepseek-ai/dsh"]` remains the fallback. Keep a concrete `devDependencies` version for local builds. The example pins the first Preview; install or update with `pnpm add -D @becomeopc/dshx@preview` instead of relying on an unpublished stable `0.2.0` range.

Remove `@deepseek-ai/dsh-client-runtime` from dependencies, peers, and `dsh.client.inject`. DSH 0.2 does not publish that package. Slot, store, settings, session, and conversation services now come from their focused packages.

## 2. Settings become a plugin Config

`defineSettings()` still declares one Schemastery schema, but it is now the plugin `Config` that DSH projects into its own Settings form. There is no namespace field and no Host registration call.

```ts
// src/settings.ts (shared by Host and Client)
import Schema from "@deepseek-ai/schemastery";
import { defineSettings } from "@becomeopc/dshx/settings";

export const runtimeSettings = defineSettings({
  schema: Schema.object({
    showActivity: Schema.boolean().default(true),
    threshold: Schema.number().default(3).min(0).max(10),
    token: Schema.string().role("secret"),
  }),
});
```

```ts
// src/host.ts
import { defineHost } from "@becomeopc/dshx/host";
import { runtimeSettings } from "./settings.js";

export default defineHost({
  config: runtimeSettings,
  setup(ctx, config) {
    const value = config?.get(); // stable reference, updated in place by live edits
  },
});
```

```ts
// src/client.tsx
import { useSettings } from "@becomeopc/dshx/client";
import { runtimeSettings } from "./settings.js";

const state = useSettings(runtimeSettings);
```

What changed:

- **No `settings` array in `defineHost`.** Pass one `config` contract or nothing.
- **No `settingsNamespace`.** DSH identifies a form by the Host profile entry id that loads the plugin. DSHX embeds that id in the Client artifact, so keep the plugin loaded through the entry declared in its bundle patch.
- **No Host `ctx.settings.register` and no `SettingsProvider`.** DSH owns the form through `SettingsForms`; the Client reads `ctx.configForms.get(entryId)`.
- **The root schema is volatile.** DSHX calls `.volatile()` on the root so every field is live. Do not mark individual fields volatile; `defineSettings()` throws if you do.
- **`set`/`unset` resolve to `boolean`.** Use `mutate(ops, expectedRevision)` for ordered edits and the revision fence.
- **Secrets are redacted on the wire.** `state.secrets` reports schema-declared positions and whether a value is set; the value itself never reaches the Client.

The Client still declares `@deepseek-ai/dsh-client-ui-settings` in `dsh.client.inject` when `useSettings` survives tree-shaking. DSHX now reports the capability as `client:config-forms` instead of `client:settings-scope`.

## 3. Conversation uses `uiConversation`

`defineConversation()` keeps its lifecycle shape, but registration moves to the official Client service:

```ts
// before (0.1)
ctx.conversationEvents.register(definition);

// after (0.2)
ctx.uiConversation.events.register(definition);
```

The renderer types now come from `@deepseek-ai/dsh-client-ui-conversation/client`. Remove `@deepseek-ai/dsh-client-runtime` from `dsh.client.inject`; keep the official conversation renderer package if you contribute components. DSHX adds `uiConversation` to the Client inject list when a definition is present, and `dshx check` reports a missing package edge.

Custom durable event types remain unsupported. Session format is now `4`; only official `SessionEventMap` keys are accepted. Name-based keys such as `command/run` and `command/done` still work in the smoke scenario.

## 4. Connection, RPC, and API hooks

Host registration now uses peer-based routing:

```ts
// before (0.1)
connection.rpc.handle(channel, handler, { authority: "loopback" });

// after (0.2)
connection.rpc.handle(channel, handler);
```

The handler receives the official `peer` fact. Client code no longer calls `connection.api`; generated Remote namespaces are available as `ctx.remote.<namespace>`, with `$on`/`$stream` for events. DSHX's `useApiQuery` and imperative API bindings keep their author-facing shape, but the capability is now `connection:peer-admission`. The API wire path and payload are unchanged from DSHX's perspective: top-level `/dshx-<hash>/<method>` channels carry the method in the DSHX envelope.

DSH 0.2 requires browser authentication. DSH hands the browser a launch token; exchange it at `/connect?token=…` for the signed session cookie before calling `/api/...`. Direct loopback requests without that cookie now fail. This matters for custom smoke runners and scripts, not for DSHX's own Client runtime.

## 5. Prompt, Commands, and Tools

- Prompt assembly now uses `personaPrefix`/`personaSuffix`; DSH allocates contribution order. DSHX keeps `definePromptSection`/`definePromptContext` and its `order` field, but treat order as a hint.
- Command input exposes `attachments` instead of `images`. A `CommandResult` may carry `sourceEventSeq`.
- Tool definitions no longer support `mode: 'both'`; native and PTC tools are declared separately.
- `ctx.codeRuntime` becomes `ctx.ptcRuntime`. `CallId` becomes `ToolCallId`. `JsonValue` comes from `@deepseek-ai/dsh-util-values`.
- DSHX re-exports the official `defineTool` unchanged, so those type names arrive with the official packages.

## 6. Manifest and bundle patches

- `manifestVersion: 1` is accepted.
- `dsh.bundle.patch` may be a string or an array of patch paths. DSHX scans every patch to resolve the Settings entry id.
- The `/invariant` subpath is gone; import supported entries from the package root, `/host`, `/client`, `/api`, `/settings`, `/experimental/conversation`, or `/tooling`.
- `create-dshx` writes `engines.dsh`; `dshx check` reports a missing or stale declaration.

## 7. Inspect and `add ui`

DSH 0.2 has no first-party runtime Slots catalog. DSHX behavior:

| Command                             | 0.2 behavior                                                                                                                |
| ----------------------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| `dshx inspect tools`                | Runtime-backed through the Host bridge                                                                                      |
| `dshx inspect services`             | Runtime-backed                                                                                                              |
| `dshx inspect events`               | Runtime-backed                                                                                                              |
| `dshx inspect configs`              | Runtime-backed                                                                                                              |
| `dshx inspect slots`                | `DSHX3204`; Slots are compile-time contracts                                                                                |
| `dshx add ui --slot X --provider Y` | Generates from explicit values and emits a warning (`DSHX6112`) because the provider catalog cannot verify the registration |

`dshx add ui` still validates the provider type entry, the Client entry, file placement, and the resulting manifest. Pass `--id`/`--order` for list Slots; the generated file is checked against the provider types by `dshx check`/`build`.

The Host bridge remains DSHX-owned and composition-scoped. It does not use the seven local DSH `inspect-bridge` commits from the development checkout.

## 8. Verification checklist

```bash
pnpm install
pnpm --filter @becomeopc/dshx test
pnpm check:all
pnpm smoke:dsh -- --dsh-source /path/to/deepseek-harness
```

`pnpm smoke:dsh` without `--dsh-source` uses npm artifacts and is useful only for diagnosing upstream publication drift. The 0.2 source smoke covers Host-only and Client-only projects, full Host/Client startup, Settings writes and revision fences, API calls, Commands, Prompt contributions, Conversation replay, HMR, Host restart, and runtime Inspect for tools/services/events/configs.
